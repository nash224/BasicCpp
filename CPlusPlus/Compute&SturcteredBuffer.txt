


상수 버퍼
	- 용량이 제한이 있음
	- 똑같은 바이트 크기의 자료가 들어오면 2개를 만드는건 효율적이지 않아서 다시 들어오는 버퍼는 만들지 않는다.

스트럭처드 버퍼
	== 이론 == 
	- 동적으로 데이터 크기를 변경할 수 있다. : 상수버퍼는 안됨, 
		=> 메모리를 아껴야함
	- 텍스처와 슬롯을 공유한다.
	- 대용량 데이터를 보낼수있음
	- 슬롯 넘버를 총 구조체의 크기로 담는다.
	- 버퍼가 몇개던 바이트 크기는 바꿀 수 없다.


	== 변수 ==
	- DataSize => 구조체의 크기는?
	- DataCount => 몇개인가?

	- Type => 사용용도는 무엇인가?


	== Desc == 
	ByteWidth : DataSize* DataCount

	- Usage --> 메모리를 보관할 장소, ex) CPU, 하드웨어, GPU 등 => 속력차이 직결

		== Srv 전용 == 
			- bingflag --> 쉐이더 리소스로 사용하겠다
			- Usage --> GPU(사용만 가능)와 Cpu에서 접근할 수 있다.

		== UAV_INC : UAV 컴퓨트 쉐이더에서 결과를 받아오는 권한
			- bindflags = 컴퓨트 전용 => 쉐이더 접근 | ㅁㅁㅁ
			- CPUAceessflags --> Cpu에서 엑세스 x => GPU에서 받았는데 값을 바꿀 필요가 없다.


	== 세팅 ==
	- 텍스처와 슬롯을 공유하기 떄문에 SRV 권한이 필요하다.

	Find(바이트)
		=> 슬롯을 찾음

	CreateAndFind
		=> 없으면 만들고 있으면 쓴다.

	CreateResize
		- 기존에 사용하던 버퍼 크기를 넘어서면 기존의 버퍼를 지우고
		- 다시 키워서 만든다.

		- SRVDesc
			- ViewDimension : 일반 버퍼에서 리소스 뷰 생성

		- SRV 또는 UAV 생성

		               

	Release
		SRV나 
		NameRes, UnNameRes 자료를 지운다

	ChangeData
		== Map ==
		Context()->Map(Buffer, 0,,, &settingResource )
		- 병렬처리로 공유해서 쓴다.
		- 중간에 수정한다면 그래픽카드를 멈춘다.

		- settingResource => 그래픽카드의 메모리가 아닌 메모리에 수정하라고 보낸 명령어다.

		== Unmap == 

		- 리소스가 적용을 끝내면 다시 움직이게 한다.
		
		

	== enum ==
		UAV_INC		컴퓨트 쉐이더에서 결과값으로 사용하겠다.
		SRV_ONLY	쉐이더에 보내는데 사용하겠다.


그래픽카드가 빠른이유
	- 수학적 계산이 빠르다.
	- 병렬처리를 많이 할 수 있다.
	- 커널이나 CPU에서 사용하는 운영체제 명령어가 없다.

Compute Shader => 파티클
	- 수학적 계산을 컴퓨트 쉐이더에 맡김 
		=> 충돌, 이동같은 연산을 맡긴다.

	- 결과값을 CPU에 받는다
		=> 결과값을 스트럭트 버퍼로 받는다.
